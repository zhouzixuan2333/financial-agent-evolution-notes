# 第一阶段：先把检索工作流评准，再谈优化

> 口径说明：本章数字是项目阶段快照，用于解释技术判断，不代表公开基准或线上长期指标。

## 1. 我接手的系统已经有一条快速链路

我最开始并不是从零搭建取数系统。已有方案大致是：

```mermaid
flowchart LR
    A[用户 Query] --> B[多维向量召回]
    B --> C[候选综合打分]
    C --> D[返回 Top1]
    D --> E[执行取数]
```

我的工作是分析这条链路为什么会错，再针对召回、排序和执行环节优化 Workflow。

它对高频、单目标问题比较有效，但隐含了一个不总是成立的假设：**语义最相似的候选，就是业务上正确的指标。** 金融问题还包含地区、频率、单位、时间范围和统计口径等约束。只要漏掉其中一项，候选看起来很相关，实际仍可能无法回答问题。

## 2. 第一件事不是改召回，而是建立 Judge

### 2.1 先看一条容易被误判的取数结果

下面用一个贯穿本章的合成 Case。国家、商品、指标代号与数值均为重新编写，输入输出也使用通用形式展示，不对应原始 Prompt、工具 Schema 或真实评测样本。

> 用户问：2024 年第一季度，甲国从乙国进口商品 X 的总量是多少？请用万吨表示。

假设标准答案使用季度总量指标，但模型找到了同一口径的月度指标：

| 对象 | 指标与数据 | 能否回答问题 |
| --- | --- | --- |
| 标准答案 | 指标 Q：甲国从乙国进口商品 X，2024 年第一季度总量为 90 万吨 | 可以直接回答 |
| 模型返回 | 指标 M：同一贸易方向、同一商品的当月进口量，1 月 25、2 月 30、3 月 35 万吨 | 完整覆盖该季度，可求和得到 90 万吨 |

如果只检查指标 ID，`M ≠ Q`，这条结果会被判错。但用户要的是季度进口总量，并没有要求必须使用指标 Q。月度值在同单位、同统计范围、无缺月和重复的条件下，已经足以计算答案。

这使我意识到，评测至少需要区分两件事：**是否命中标准指标，以及返回的数据是否足以回答原问题。** LLM Judge 用来补充后一个判断。若模型已经生成最终答案，还要单独检查它有没有正确计算和使用这些数据；“取回了正确数据”不等于“最终回答一定正确”。

### 2.2 Judge 看什么，怎样判断

我构建 Judge 时，重点是把指标名称、频率、单位、时间范围和可计算关系放回用户问题中判断。只给它两个指标名，让它判断“像不像”，仍会遗漏原来的业务约束。

以这道题为例，可以把判定所需的信息整理成下面四部分：

| 输入 | 本例内容 | 用途 |
| --- | --- | --- |
| 原始问题 | 甲国、从乙国进口、商品 X、2024 年第一季度、总量、万吨 | 确定必须满足的条件 |
| 参考答案及口径 | 季度指标 Q，90 万吨 | 提供比较依据，同时允许等价取数路径 |
| 实际返回证据 | 月度指标 M，1—3 月的日期、数值、单位与指标说明 | 判断覆盖是否完整、是否能够计算 |
| 最终回答（若有） | “第一季度共进口 90 万吨” | 检查回答是否与已取回数据一致 |

下面是这一 Case 的判定过程。它用来说明规则如何作用，不是原始 Judge Prompt：

```text
1. 主体与贸易方向：甲国从乙国进口，符合。
2. 商品与指标类型：商品 X 的数量，不是金额，符合。
3. 时间覆盖：2024 年 1、2、3 月齐全，没有重复月份。
4. 单位与统计口径：均为万吨、同统计范围的当月值，可以相加。
5. 可计算关系：25 + 30 + 35 = 90，与季度总量一致。

判定：返回数据足以回答问题。
理由：虽然没有命中标准指标 Q，但指标 M 提供了完整、可加的月度数据。
若最终回答为 90 万吨，则回答与取数证据也一致。
```

Judge 也不能因为“数值接近”或“名字相关”就放宽条件。稍微修改这个 Case，结论就会不同：

| 返回结果 | 应怎样判断 | 原因 |
| --- | --- | --- |
| 同口径的 1—3 月当月值：25、30、35 万吨 | 数据充分 | 三个月可加，得到季度总量 |
| 甲国从所有国家进口商品 X 的季度总量：450 万吨 | 不满足问题 | 缺少贸易伙伴“乙国”的限制 |
| 甲国从乙国进口商品 X 的季度金额：360 万元 | 不满足问题 | 用户问数量，金额不能直接代替数量 |
| 只有 1 月和 2 月的当月值：25、30 万吨 | 数据不完整 | 缺少 3 月，不能推断季度总量 |
| 1—3 月的年内累计值：25、55、90 万吨 | 不能把三项相加 | 本例应使用 3 月末累计值 90；相加会重复计算 |

因此，“月度数据可以回答季度问题”是一条带条件的规则。存量、比率和累计值有各自的计算方式；如果返回证据没有说清口径，就不足以确认可加性，需要进一步核实。

### 2.3 我怎样建立并校准这把尺子

Judge 的建立包含判定规则和人工校准两部分。我先针对原有指标匹配方式容易误判的 Case，补充业务判断维度，再通过人工争议 Case 迭代规则。按这个过程来看，一次规则迭代可以拆成：

1. **把分歧落到具体证据上。** 对照原问题、参考答案和实际取数结果，先弄清人工与 Judge 究竟在哪个条件上不同意。
2. **将个别 Case 归纳成规则。** 例如，月度当期值覆盖完整季度时可以求和，但累计值不能重复相加；商品相同也不能忽略贸易伙伴或数量/金额的区别。
3. **回看规则会不会放过另一类错误。** 接受等价指标后，还要检查漏月份、错单位、错主体等反例，避免把“允许计算替代”写成“相关就算对”。
4. **用独立样本复测。** 规则在争议样本上变好以后，还需要看它对其他问题的判断是否可靠。

上面的月度、累计值和缺月份例子是对校准思路的合成演示，不是历史迭代批次的逐项记录。历史材料能确认的是：我使用 LLM-as-a-Judge 补充业务条件与可计算关系判断，并通过人工争议 Case 持续校准；后续独立 100 条复测中，与人工判定一致率达到 93%。

这把尺子的价值是让新旧链路可以围绕同一个问题比较，并留下可追查的判因。为了使比较有效，两条链路需要使用相同的 Judge 版本和判定规则；Judge 应读取各自实际返回的证据，不能替某条链路补上它没有取回的数据。

## 3. 一个 Case 如何暴露语义召回的局限

沿用上面的季度进口问题，再看它在原链路中怎样出错。这里给出一组示意候选，排名用于解释错误位置，不代表真实相似度分数或工具返回。

### 3.1 原链路：召回了相关候选，却把约束不完整的结果排在前面

```text
输入：2024 年第一季度，甲国从乙国进口商品 X 的总量是多少？
  ↓ 多维向量召回与综合打分
Top1：甲国从所有国家进口商品 X 的季度总量
候选：甲国从乙国进口商品 X 的季度金额
候选：甲国从乙国进口商品 X 的当月进口量
  ↓ 选取 Top1，执行取数
返回：第一季度进口总量 450 万吨
  ↓ 作为用户问题的答案
“2024 年第一季度，甲国从乙国进口商品 X 共 450 万吨。”
```

这里最迷惑的地方是，450 万吨确实是取回的数值，并非模型凭空编造。但它属于“从所有国家进口”，最终回答却将它套在“从乙国进口”的问题上。Top1 命中了国家、商品、季度和数量，却遗漏了贸易伙伴限制。

按前面的 Judge 思路检查，失败理由应当是“返回数据的贸易伙伴范围不符”，而不是简单说答案数值不等于 90。即使另一个统计范围的数值碰巧也是 90，也不能据此判对。

### 3.2 看候选和执行记录，才能决定改哪一层

在这个示例中，能回答问题的月度指标已经进入候选，因此首先要检查候选筛选与后续计算，而不是只增加召回数量。如果完整候选里根本没有该指标，才需要进一步检查 Query 表达和召回覆盖。

进一步看完整候选后，可以把问题分成三层：

| 观察到的现象 | 更可能的问题 | 优先检查的环节 |
| --- | --- | --- |
| 正确指标没有进入任何一路 TopK | 召回覆盖不足 | Query 表达、召回通道、索引描述 |
| 正确指标已经进入 TopK，但没有排到 Top1 | 候选区分度不足 | 综合打分、业务条件判断 |
| Top1 指标正确，但最终数据或答案错误 | 执行链路错误 | 参数、时间范围、聚合计算、工具调用 |

这是根据 Case 得到的工程归因框架，不是严格的因果消融。它的价值在于避免把所有错误都简单归咎于 embedding。

## 4. 将线上输入输出搬进可回放 Workflow

优化后的验证链路是：

```mermaid
flowchart LR
    A[保留原始 Query] --> B[拆成可执行子问题]
    B --> C[多类接口并行召回]
    C --> D[LLM 筛选与聚合]
    D --> E[生成最终答案]
    E --> F[Judge 对比新旧方案]
    F -.失败原因回流.-> B
```

### 4.1 优化后的链路：保留原问题，让候选回到业务条件下比较

还是查询甲国从乙国进口商品 X 的季度总量。下面把问题拆解、多路召回、筛选与计算展开；Query 表达和候选均是合成示意，多路接口的真实名称与参数省略。

**第一步：保留原问题，展开几种可执行的查询表达。**

```text
原问题的硬约束：
甲国 ← 从乙国进口；商品 X；2024 年第一季度；数量；万吨。

查询表达 A：甲国从乙国进口商品 X，季度数量。
查询表达 B：甲国从乙国进口商品 X，2024 年 1—3 月当月数量。
查询表达 C：甲国从乙国进口商品 X，2024 年累计数量。
```

这些表达围绕同一目标寻找直接指标或可计算的替代指标。它们不是三个独立的用户问题，也不对应固定数量的接口；生成子查询后仍要保留原始问题，防止“从乙国进口”在改写中丢失。

**第二步：通过多类接口并行召回，汇合候选。**

| 查询方向 | 示意候选 | 聚合时需要检查的事 |
| --- | --- | --- |
| 季度数量 | 全部贸易伙伴的季度数量、乙国的季度金额 | 名称相近，但贸易伙伴或指标类型不符 |
| 月度数量 | 乙国的商品 X 当月进口量 | 符合主体与数量约束，可以继续核验时间覆盖 |
| 累计数量 | 重复出现的月度候选、其他贸易伙伴的累计量 | 识别重复候选，不能把累计量与当月量直接混加 |

**第三步：LLM 对照原问题筛选与聚合。**

“全部贸易伙伴”的数量和“乙国”的金额都应被排除。对于保留下来的月度指标，需要取得或核验 1—3 月的实际值、单位与口径；仅找到指标名称还不足以宣告任务完成。

本例中，符合条件的数据为 25、30、35 万吨，可以计算 `25 + 30 + 35 = 90`。最终回答可以写成：

> 2024 年第一季度，甲国从乙国进口商品 X 共 90 万吨，由 1 月 25、2 月 30、3 月 35 万吨相加得到。

这里的求和是说明计算应如何核验，不表示必须让 LLM 自由心算；计算结果应能够从工具数据复算。

**第四步：用同一把 Judge 比较两条链路。**

| 检查项 | 原链路 | 优化后的示例链路 |
| --- | --- | --- |
| 最终使用的数据 | 全部贸易伙伴的季度进口量 | 从乙国进口的 1—3 月当月量 |
| 贸易伙伴约束 | 不满足 | 满足 |
| 时间与数量口径 | 季度数量，但统计范围不符 | 月度数量覆盖季度，且口径可加 |
| 最终答案 | 450 万吨 | 90 万吨，并说明计算依据 |
| Judge 判因 | 取数范围与问题不一致 | 数据充分，计算与回答一致 |

这个 Case 展示的是改造机制：子查询增加找到正确口径的机会，候选聚合避免直接把综合分最高的结果当答案，最后再核验数据与计算。它不证明某一个修改贡献了多少收益，整体效果仍由下面的批量评测判断。

### 4.2 把示例中的检查变成可回放记录

每条样本保留输入、工具调用、候选结果、最终答案和 Judge 判因。对于上面的错误，可以先查看 Top1 是否带有“乙国”约束，再检查正确月度指标有没有进入候选，最后核对日期、单位和计算。这使指标下降时能够回到具体环节定位问题，而不是只得到一个“错”的标签。

Judge 在这里是验证链路的一部分，用于比较输出和反馈错误，不代表每次线上用户请求都必须额外调用 Judge。

### 4.3 批量评测结果

在 1,385 条真实分布问句上，结果如下：

| 评测口径 | 原方案 | 优化后 |
| --- | ---: | ---: |
| 严格口径 | 53.57% | 74.66% |
| 平均口径 | 61.48% | 79.32% |
| 最高口径（源表名称） | 69.39% | 83.97% |

按源表的平均口径，正确率提升 17.84 个百分点，说明传统检索链路仍然存在明显的工程优化空间。

这里保留“严格、平均、最高”三个历史名称。当前公开材料没有附完整判分函数，所以不能仅根据数字关系，把平均口径定义为上下界均值，或把最高口径解释成理论上界。前面的季度/月度示例只解释 Judge 的业务动机；三种历史口径的结果与边界统一见 [实验索引 E2](06-experiment-index.md)。

## 5. TopK 实验告诉我的不只是参数应该设多少

| 候选深度 | 平均正确率 |
| ---: | ---: |
| Top40 | 78.81% |
| Top10 | 79.32% |
| Top5 | 79.10% |

Top10 与 Top5 只差 0.22 个百分点，继续扩大到 Top40 也没有更好。在这轮固定方案与数据上，没有观察到扩大候选深度的明显收益。候选噪声是一种可能解释，仍需候选分析或消融支持；这些结果也不足以证明 Top10 显著优于 Top5，或检索路线已经达到普遍上限。

与此同时，跨地区批量取数、多个相关指标组合和模糊表达仍然需要模型主动拆解、探索与纠错。它们不是一次 TopK 召回自然能够解决的问题。

所以这一阶段的最终判断是：

> 优化后的 Workflow 适合高频、单目标问题；对于需要多步探索的长尾问题，应该保留快速链路作为候选方案，同时引入能够沿结构主动寻址的 Agent。

这成为下一阶段转向目录树 Agent 和可复用 Skill 的直接原因。

## 6. 这一阶段留下的方法论

1. 先建立可信评测，再谈模型或 Workflow 优化。
2. 把召回、排序和执行错误分开，不用单一指标解释所有失败。
3. 总分判断是否变化，完整轨迹和 Badcase 解释为什么变化。
4. TopK 敏感性用于观察当前配置的候选深度收益，并与长尾失败轨迹一起支持下一步技术判断。
5. 技术路线的切换应由可复现的 Case 和实验现象推动，而不是由框架热度推动。
