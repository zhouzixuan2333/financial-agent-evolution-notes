# 第二阶段：让 Agent 沿目录主动寻址，并把方法沉淀成 Skill

> 口径说明：本章数字是项目阶段快照；示例已经重新编写，不对应真实客户或原始业务数据。

## 1. 为什么优化后的检索 Workflow 仍然不够

第一阶段解决了大量高频、单目标问题，但剩余 Badcase 中出现了一类不同的任务：用户不是寻找一个指标，而是要求覆盖多个地区、多个口径或一组相关目标。

例如：

> 查询某城市全部下属地区在指定季度的同一经济指标及其累计同比。

这类问题至少包含三步：先确认下属地区集合，再为每个地区定位相同口径的指标，最后检查结果是否完整。多次改写 Query 可能召回大量重复候选，却没有增加实际地区覆盖。

结合当时 TopK 实验没有明显增益，以及剩余 Case 的覆盖与恢复问题，我得到的工程判断是：

> 长尾取数不只是相关性排序问题，还需要在结构化空间中探索、记住已经覆盖的目标，并在局部失败后换路径继续找。

因此，第二阶段引入目录树寻址 Agent，专门补足需要多步探索的任务。这个选择由候选实验与失败轨迹共同支持，不能仅由三个 TopK 分数推出。

## 2. 从原有 Workflow，到 Agent 可调用的工具

指标记录、目录节点和时间序列的关系，以及同名多 ID、同节点混合口径等现象，先见[底层数据与目录结构](00-project-map.md#0-底层数据与目录结构)。

在原有 Workflow 的基础上，我把指标检索封装成搜索工具，让 Agent 根据返回结果决定是否继续查找。原有检索能力承担一轮候选召回与排序，Agent 负责拆解目标、判断候选、补齐缺项和决定何时取数。

Agent 使用三类动作。下面是公开代称，不对应真实接口名：

| 动作 | 输入 | 返回 |
| --- | --- | --- |
| `SEARCH` | 搜索词、原始问题、候选数量上限 | 候选指标及名称、ID、频率、单位、来源、父节点等 |
| `EXPAND_PATH` | 已命中候选的父节点及所属模块 | 同目录下的相关指标 |
| `FETCH_DATA` | 已确认的指标 ID 和时间范围 | 实际时间序列数据 |

底层指标库已经按分类把指标挂在不同节点下。搜索结果中的父节点 ID，相当于告诉 Agent：“这条指标属于哪一组。”用这个 ID 查询，就能列出同一节点下的其他指标。例如：

```text
父节点 900（示意 ID）
├── 居民第一阶梯：供水单价
├── 居民第二阶梯：供水单价
├── 居民第三阶梯：供水单价
├── 非居民：供水单价
├── 特种行业：供水单价
└── 居民：污水处理费
```

这里的“展开目录”，就是按搜索结果中的父节点 ID 列出已有的同级指标。同一节点也会混有不同统计对象和口径，同类指标还可能分散在其他节点。**底层目录和数据质量无法由我们改变，因此优化集中在 Agent 如何搜索、判断和恢复。** 父节点帮助缩小候选范围，最终仍需逐项核对。

## 3. 搜索怎样封装，为什么传两个 Query

Agent 先从问题中提取主体、指标、口径和时间；多目标问题拆成若干具体搜索。一次搜索保留两份文本：

| 信息 | 例子 | 作用 |
| --- | --- | --- |
| 原始问题 | 查询某市指定月份居民各阶梯、非居民和特种行业的供水单价差异 | 保留完整需求，供候选重排参考 |
| 当前搜索词 | 某市 非居民 供水单价 | 聚焦这一轮要找的目标，传给检索服务 |

**召回时可以简化搜索词，判断候选时仍要保留原始条件。** 例如脚本可能去掉部分口径后缀来扩大召回，但重排和最终选择时仍需检查口径，不能因为放宽搜索就接受错误指标。时间范围主要在取数时使用；频率、来源、单位等仍要在选指标时核对。

搜索工具的处理过程是：

```text
接收搜索词和候选上限 K
  → 按规则生成搜索变体，调用指标检索服务
  → 合并候选，按指标 ID 去重
  → 结合原始问题与当前搜索词重排
  → 返回最多 K 个候选及元数据
```

当前脚本默认上限为 10，也可以指定 5 等其他数量；实际命中不足时返回更少。默认本地重排依据关键词、重要口径词、频率等规则打分，不需要额外调用大模型。

这个阶段返回的是候选，不是最终选定的指标。排序靠前只能说明值得优先检查，模型还要结合完整需求判断。例如，查询全国整体投资时，“某省投资”或“民间投资”即使排第一，也不能直接选用。

## 4. 跟着命令看：搜索、补齐，再取数

> 比较某市 2025 年 4 月居民三个阶梯、非居民和特种行业的供水单价，均不含污水处理费。

下面用重新编写的命令和返回示意串起流程。`indicator_tool.py` 是示意脚本名，ID 也是假设值，本仓库不提供可执行接口。`search`、`list-by-path`、`fetch / batch-fetch` 分别对应前面的搜索、目录展开和取数动作。

**① `search`：找候选指标。**

Agent 先列出五项目标，再分别搜索居民阶梯、非居民、特种行业。以非居民为例：

```bash
python indicator_tool.py search \
  --query "某市 非居民 供水单价" \
  --original-query "比较某市2025年4月居民三个阶梯、非居民和特种行业的供水单价，均不含污水处理费" \
  --limit 5 \
  --format json
```

- `--query`：这一轮具体搜什么。另两次换成“某市 居民 阶梯供水单价”和“某市 特种行业 供水单价”。
- `--original-query`：三次都保留同一个完整问题，供重排参考。
- `--limit 5`：最多返回五个候选；`--format json`：返回结构化结果，便于模型读取名称、ID、频率和父节点等信息。

独立搜索可以并发，一个搜索也可能命中多个目标。假设三次结果合并后，模型确认了以下情况：

| 目标 | 已确认的指标 ID（示意） | 状态 |
| --- | --- | --- |
| 居民第一、第二、第三阶梯供水单价 | 101、102、103 | 三项已匹配 |
| 非居民供水单价 | 104 | 已匹配 |
| 特种行业供水单价 | — | 搜索为空，尚缺一项 |

这里的“确认”需要检查城市、供水对象、是否含污水处理费及数据时间覆盖，不能只看排名。搜索返回的仍是指标元数据，尚未取得指定月份的价格。

**② `list-by-path`：利用父节点找缺项。**

假设已命中的供水指标都带有父节点 `900`、所属模块 `1`，Agent 直接使用返回的这两个值：

```bash
python indicator_tool.py list-by-path \
  --parent-id 900 \
  --module 1 \
  --contains "特种" \
  --format json
```

`--parent-id` 指定查哪个目录，`--module` 指定所属模块；`--contains` 在返回子项中按名称等文本过滤，不是语义搜索。这里仅保留包含“特种”的项，得到如下示意结果：

| 指标 ID | 候选名称 | 模型判断 |
| --- | --- | --- |
| 105 | 某市：特种行业：供水单价（不含污水处理费） | 符合缺失目标 |
| 106 | 某市：特种行业：污水处理费 | 口径不符，排除 |

**同父节点提供查找线索，最终仍要选对指标。** 如果返回为空，先检查过滤条件和入口；仍找不到，就参考已命中指标的名称结构定向补搜，或尝试其他入口。

**③ `batch-fetch`：把确认的 ID 换成真实数据。**

五项目标全部匹配后，一次提交五个 ID 和日期范围：

```bash
python indicator_tool.py batch-fetch \
  --indicator-ids "101,102,103,104,105" \
  --start-date 20250401 \
  --end-date 20250430 \
  --workers 5 \
  --format json
```

`--indicator-ids` 是已选指标；起止日期限定数据范围；`--workers 5` 控制脚本内批量取数的并发数。只取一个指标时，可用 `fetch --indicator-ids "101"`，同样传入日期范围。

工具返回时间序列后，再核对指标与日期、检查空数据，之后才计算价差、统一展示单位并附来源。若目标仍缺失，要明确列出，不能用错误口径代替。

搜索已找齐时可以直接取数，无须展开目录；单指标漏召回时也可以走目录补找。Agent 的作用，就是根据当前结果决定下一条命令。

## 5. 从 Badcase 到 Skill：固定搜索、选择和恢复方法

有了工具，模型仍可能选错口径、重复搜索或提前结束。我将失败轨迹中的问题转成操作规则，逐步沉淀进 Skill：

| 遇到的问题 | Skill 中的处理方法 |
| --- | --- |
| 搜索太泛，返回很多候选却没查全 | 先列主体、指标和口径的目标清单；地区集合参考标准表，再定向搜索 |
| 改写后丢失原始限制 | 搜索词用于召回，完整问题保留给重排和候选判断 |
| 名称相似或排名第一就选中 | 核对主体、指标、口径、频率及时间覆盖，建立目标到 ID 的映射；近似项只作补搜线索 |
| 反复改词，仍是同一批候选 | 利用已命中的相关目录补找；仍缺失时，复用名称结构定向补搜 |
| 一次为空就放弃，或无差别重试 | 搜索为空时缩词、换同义词；目录为空时检查过滤条件和入口；取数为空时检查日期范围 |
| 找到部分结果就结束 | 取数前检查目标覆盖，取数后核对实际返回；缺项明确说明，不能用部分结果冒充完整比较 |

例如，水价任务中只找到四项时，单纯提醒“继续查完整”不够。把五项目标列出来、保留已匹配 ID、只为缺项补找，才让这条经验成为可执行的步骤。这套方法可以复用于多个地区、行业或期限的查询。

Skill 承载任务操作说明，并配合参考资料和调用脚本使用。候选是否真正符合问题、下一步采用哪种查法，仍由模型判断；去重、本地重排、目录过滤和批量取数等稳定操作由脚本执行。**写进 Skill 的规则不等于代码已强制保证，是否遵守仍要检查轨迹。**

效率主要来自定向搜索、目录补找、只查缺项，以及独立请求并发和批量取数。并发减少等待，却不会减少请求总量；模型仍可能重复查询或额外扩展目标。因此需要同时检查覆盖率、调用次数、耗时和 Token，不能仅凭规则推断提速效果。

完成条件与执行预算也要分开。Skill 判断是否查全，执行层用超时等限制兜底；当前评测支持配置超时，但默认不启用。覆盖集合求差、重复动作检测等仍可进一步交给代码。

## 6. Skill 怎样执行，又怎样验证修改有效

Agent Runtime 是负责运行模型与工具交互的程序，项目使用过 Claude Code SDK 和 OpenCode。例如，模型发现还缺特种行业的供水单价，就取出已找到指标返回的父节点 ID `900` 和模块 `1`，生成第 4 节的 `list-by-path` 命令。Runtime 执行命令并送回同一节点下的指标列表，模型再从中挑选符合要求的指标。工具负责查数据，模型负责判断，Runtime 把调用与反馈接起来。

我的迭代过程是：**检查失败轨迹 → 定位错误决策 → 修改 Skill 或工具 → 回归评测。** 对漏查问题，检查目标集合和提前结束的位置；对错口径问题，检查候选与 ID 的选择。修改后既复查原来的 Badcase，也跑其他同类任务。

比较一次修改时，评测固定其余数据、模型、Skill 或 Runtime 配置，保存调用参数、结果、耗时与 Token，并计算任务得分。这套轨迹与评测流程，也为后续训练数据构造和模型验收提供了基础。

## 7. 阶段结果与下一步

早期单项能力迭代记录中：

| 方案 | F1 |
| --- | ---: |
| 快速检索参考方案 | 71.31 |
| 目录树 Agent | 91.68 |
| 提升 | +20.37 |

这是早期整体方案的阶段结果，不能把提升分别归因于上面每条规则，也不能将后续 Skill 修改都计入这次实验。

这一阶段形成了利用已有检索和目录主动寻址、通过 Skill 指导执行并用轨迹持续迭代的工作方式。但高能力外部模型的成本和延迟仍限制了使用范围，下一阶段便转向：把有效的 Agent 行为构造成训练数据，让专用模型学会这些查法。
