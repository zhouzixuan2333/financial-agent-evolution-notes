# 第二阶段：让 Agent 沿目录主动寻址，并把方法沉淀成 Skill

> 口径说明：本章数字是项目阶段快照；示例已经重新编写，不对应真实客户或原始业务数据。

## 1. 为什么优化后的检索 Workflow 仍然不够

第一阶段解决了大量高频、单目标问题，但剩余 Badcase 中出现了一类不同的任务：用户不是寻找一个指标，而是要求覆盖多个地区、多个口径或一组相关目标。

例如：

> 查询某城市全部下属地区在指定季度的同一经济指标及其累计同比。

这类问题至少包含三步：先确认下属地区集合，再为每个地区定位相同口径的指标，最后检查结果是否完整。多次改写 Query 可能召回大量重复候选，却没有增加实际地区覆盖。

结合当时 TopK 实验没有明显增益，以及剩余 Case 的覆盖与恢复问题，我得到的工程判断是：

> 长尾取数不只是相关性排序问题，还需要在结构化空间中探索、记住已经覆盖的目标，并在局部失败后换路径继续找。

因此，第二阶段引入目录树寻址 Agent，专门补足需要多步探索的任务。这个选择由候选实验与失败轨迹共同支持，不能仅由三个 TopK 分数推出。

## 2. 已有目录是什么，我们能改什么

底层指标库已经按主题、来源等组织了分类目录。指标挂在目录节点下，每个指标有用于取数的 ID，以及名称、频率、单位等信息。同一目录下的指标，可以通过父节点一起查出来。下面是简化示意：

```text
地区经济 → 某来源 → 某经济指标：季度累计值
                   ├── 地区 A → 指标 ID
                   ├── 地区 B → 指标 ID
                   └── 地区 C → 指标 ID
```

搜索命中 A 的指标后，可以利用它的父节点找到 B、C 的相关指标，不必每次都从全库重新搜。这就是目录对 Agent 的价值。

但目录并不总是整齐：同一地区有多个统计口径，同类指标可能分散在不同来源的目录里，还存在别名和重复记录。**底层目录和数据质量无法由我们改变，因此优化集中在 Agent 侧：怎样使用已有目录、辨别候选、补齐缺项，以及在失败后换一种查法。** 同父节点只是线索，不能直接保证口径正确。

## 3. Agent 查什么，怎样根据结果决定下一步

Agent 使用三类工具动作。下面是公开代称，不对应真实接口名或参数：

| 动作 | 查什么 | 返回什么 |
| --- | --- | --- |
| `SEARCH_PATH` | 带地区和口径的指标关键词 | 候选指标及其 ID、父节点、频率等信息 |
| `EXPAND_PATH` | 已命中指标所在的目录 | 同一目录下的相关指标 |
| `FETCH_DATA` | 已确认的指标 ID 和时间范围 | 实际时间序列数据 |

这里的搜索仍然返回候选指标；父节点信息让 Agent 能从这个命中项继续找相关指标。查询时只接收候选和局部目录，不需要把约 900 万指标装入上下文。

以一个合成任务为例：

> 查询某城市全部下属地区在指定季度的 GDP 累计值及累计同比。

**先定目标，再搜索。** Agent 根据地区标准表确认有 A、B、C、D 四个地区，形成“4 个地区 × 2 个口径”的 8 项清单。分别生成“地区 A GDP 累计值”“地区 A GDP 累计同比”等搜索词，并发执行独立搜索。时间范围留到取数时使用，候选的频率和口径则在筛选时核对。

**看结果，决定展开还是补搜。** 假设第一轮确认了 A、B 的累计值和 A、B、C 的累计同比，共 5 项。接下来这样处理：

| 当前结果 | Agent 的判断与下一步 |
| --- | --- |
| A、B 的累计值已确认，C、D 缺失 | 展开已命中的累计值目录，筛选 C、D，并核对口径 |
| 累计值补齐了，仍缺 D 的累计同比 | 展开已命中的累计同比目录，寻找 D |
| 该目录没有 D，或只有 D 的其他口径 | 参考已确认指标的名称结构，定向搜索“地区 D GDP 累计同比”，尝试其他入口 |
| 8 项均找到对应 ID | 批量取数，核对返回指标名、时间和数据是否齐全 |
| 补搜后仍无法确认 D 的累计同比 | 列明缺项，不用其他口径替代；不能据此给出完整的地区排名 |

**“主动寻址”体现在这些选择上：模型根据工具返回和剩余目标，决定展开哪个目录、补搜哪一项、何时取数或说明缺失。** 每个任务实际经过的步骤可以不同。

## 4. 从 Badcase 到 Skill：把有效查法固定下来

有了工具，Agent 仍可能选错指标、重复搜索或提前结束。我把这些失败转成具体的操作规则，沉淀到 Skill 中，让同类任务可以复用。

以“只查到部分地区就回答”为例，早期做法是提醒模型继续寻找兄弟节点，但模型仍可能把已找到的结果当作全部结果。后续将它改成明确的步骤：

```text
搜索前：列清地区和口径，确定目标集合。
选指标时：记录每个目标对应的候选与 ID，不能只看排名。
取数前：检查哪些目标尚未匹配，只为缺项继续查找。
取数后：核对实际返回的指标，无法补齐则明确说明。
```

在上面的例子里，这意味着找到 5 项时，Agent 能明确知道还缺哪 3 项，而不是凭“结果看起来不少”决定结束。这条规则也适用于多个国家、多个期限等集合查询。

对照早期与后续 Skill，主要沉淀了以下方法：

| 要解决的问题 | 写进 Skill 的查法 |
| --- | --- |
| 搜索太泛，候选多但目标覆盖少 | 先拆主体、指标和口径，用具体目标搜索；地区范围先查标准表 |
| 名称相近就选中，取错频率或口径 | 核对候选原名和属性，建立目标到 ID 的对应关系；近似项只作补搜线索 |
| 反复改写整句，仍漏掉部分目标 | 优先沿已命中的同源目录补齐；仍缺失时，复用名称结构定向补搜 |
| 一次为空就放弃，或无差别重试 | 搜索为空时缩词、换同义词；目录为空时检查过滤条件和入口；取数为空时检查日期范围 |
| 查到部分结果就结束 | 取数前检查目标覆盖，取数后检查实际返回；缺失明确列出 |

Skill 承载的是这些任务操作说明，并配合参考资料和调用脚本使用。它规定何时采用某种查法，模型结合当次结果作判断。我迭代的是可复用的搜索、补齐和恢复策略，而不是为每一道题写死答案或调用顺序。

## 5. 怎样控制查询成本

增加检查会有成本，因此优化也要减少无效动作。当前 Skill 要求独立搜索并发执行，已确认的 ID 交给脚本批量取数；工具侧完成候选 ID 去重、默认本地重排、目录过滤和精简输出，减少重复候选与串行等待。

但并发不会减少请求总量，严格匹配也会增加判断。沿目录补齐、只查缺项，是为了避免反复全库搜索；目标数量很多时仍可能很慢，不能仅凭规则推断提速效果。

完成条件与执行预算也要分开：Skill 判断任务是否查全，执行层用超时等限制兜底。当前评测支持配置超时，但默认不启用；覆盖集合求差、重复动作检测等仍可进一步交给代码。后续验收需要同时看覆盖率、调用次数、耗时和 Token。

## 6. Skill 怎样执行，又怎样验证修改有效

Agent Runtime 是负责运行这套交互的程序，项目使用过 Claude Code SDK 和 OpenCode。例如，模型依据 Skill 决定展开 A 所在的目录，Runtime 执行工具调用，把返回结果送回模型；模型再判断是否已找到 C、D。工具负责查数据，模型负责判断，Runtime 负责把调用与反馈接起来。

我的迭代过程是：**检查失败轨迹 → 定位错误决策 → 修改 Skill 或工具 → 回归评测。** 对漏查问题，检查目标集合和提前结束的位置；对错口径问题，检查候选与 ID 的选择。修改后既复查原来的 Badcase，也跑其他同类任务，避免只修好一道题。

评测程序固定数据、模型、Skill 版本和 Runtime，保存调用参数、结果、耗时与 Token，并计算任务得分。这样才能区分策略修改、模型变化和运行框架带来的影响。这套轨迹与评测流程，也为后续训练数据构造和模型验收提供了基础。

## 7. 阶段结果与下一步

早期单项能力迭代记录中：

| 方案 | F1 |
| --- | ---: |
| 快速检索参考方案 | 71.31 |
| 目录树 Agent | 91.68 |
| 提升 | +20.37 |

这是早期整体方案的阶段结果，不能把提升分别归因于上面每条规则，也不能将后续 Skill 修改都计入这次实验。

这一阶段形成了利用目录主动寻址、通过 Skill 约束执行并用轨迹持续迭代的工作方式。但高能力外部模型的成本和延迟仍限制了使用范围，下一阶段便转向：把有效的 Agent 行为构造成训练数据，让专用模型学会这些查法。
